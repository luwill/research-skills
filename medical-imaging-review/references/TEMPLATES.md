# Review Project Templates

These templates define the artifact contracts used by WORKFLOW.md. Run the initializer first, then complete its generated files in place; do not replace or overwrite an existing project. Never copy example values into a manuscript as facts.

Supported route values are **narrative**, **method-survey**, **scoping**, and **systematic**. The systematic route in this skill is qualitative; quantitative pooling and overviews of reviews require a separate specialist workflow.

---

## Required project layout

~~~text
review_project/
└── <topic-slug>-<YYYYMMDD-HHMMSS>-<8hex>/
    ├── review_config.yaml
    ├── REVIEW_CONTEXT.md
    ├── IMPLEMENTATION_PLAN.md
    ├── PARADIGM.md
    ├── manuscript.md
    ├── references.bib
    ├── claim_ledger.csv
    ├── AI_USE_DISCLOSURE.md
    ├── protocol_deviations.md
    ├── EXPERT_SIGNOFF.md
    ├── protocol/
    ├── search/
    ├── screening/
    ├── extraction/
    ├── risk_of_bias/
    ├── certainty/
    ├── adjudication/
    ├── reporting/
    ├── source_notes/
    ├── review_outputs/
    └── rendered/
~~~

The initializer always creates the listed common files and directories. It may additionally create route-specific files described below. **style_profile.json is optional and is not generated by default.**

Create a project with the initializer instead of manually allocating the directory:

~~~bash
python3 <skill_dir>/scripts/init_review_project.py --parent . --name <topic-slug> --route <narrative|method-survey|scoping|systematic>
~~~

`<topic-slug>` must be lowercase kebab case. The initializer uses a UTC timestamp and eight lowercase hexadecimal characters, producing **review_project/<topic-slug>-<YYYYMMDD-HHMMSS>-<8hex>/**. It refuses to overwrite an existing target. Preserve that generated path exactly.

Route-specific files generated by the initializer are:

- **narrative** and **method-survey**: search/narrative_exploration_log.csv and search/selection_rationale.md;
- **scoping** and **systematic**: protocol/PROTOCOL.md, search/search_plan.md, search/search_log.csv, search/deduplication_log.csv, screening/screening_decisions.csv, screening/full_text_exclusions.csv, screening/calibration_log.md, adjudication/conflict_log.csv, and reporting/flow_counts.json;
- **scoping only**: extraction/charting_table.csv and reporting/PRISMA_ScR_checklist.md;
- **systematic only**: extraction/study_characteristics.csv, extraction/critical_data.csv, extraction/cohort_linkage.csv, risk_of_bias/assessments.csv, risk_of_bias/decision_rules.md, certainty/assessments.csv, human_review_gate.json, and reporting/PRISMA_2020_checklist.md.

  risk_of_bias_tools: []
  certainty_framework: null

  working_syntax: "pandoc-citekey"
  target_csl: null

human_review:
  screeners: []
  extractors_or_charters: []
  adjudicator: ""
  risk_of_bias_reviewers: []
  certainty_reviewers: []
  gate_path: null  # The initializer writes "human_review_gate.json" for systematic.

ai_assistance:
  used: "unknown"
  uses: []
  disclosure_path: "AI_USE_DISCLOSURE.md"
  human_decision_authority_confirmed: false

delivery:
  format: "markdown"
  project_status: "planning"
  audit_profile: null
~~~

Validation rules:

- route is immutable after collection starts;
- project_dir is `.` and project_dir_base is `review_config_directory`, so the value unambiguously resolves to the containing collision-safe project even when `--parent` is elsewhere;
- delivery.audit_profile remains null unless an optional populated JSON profile exists;
- systematic route points human_review.gate_path to human_review_gate.json;
- every conduct/reporting/primary-study/RoB list item is a mapping with exactly the fields in `standard_record_fields`; `certainty_framework` is either the same mapping or null;
- human roles are completed before their route-specific work begins;
- before formal evidence collection or sign-off, ai_assistance.used is resolved to boolean true/false and human_decision_authority_confirmed is true;
- an AI model, bot, agent, or automation ID is not a human reviewer ID.

Every item in `conduct_guidance`, `review_reporting_guidance`, `primary_study_reporting_frameworks`, and `risk_of_bias_tools` uses this record contract; `certainty_framework` is either one such object or `null`:

~~~yaml
title: "<official title>"
version: "<version or publication year>"
url: "<official URL>"
accessed_at: "<ISO-8601 date>"
applicability: "<why and where it applies in this project>"
replaces: "<superseded tool/version or null>"
~~~

Do not store standards as bare names because version and role would become unauditable.

## Stable citekey and references.bib contract

Working citations use Pandoc syntax:

~~~markdown
This result was evaluated on an independent cohort [@surname2024-shorttopic].

Several sources support the broader observation [@surname2024-shorttopic; @other2025-related].
~~~

Create citekeys as:

~~~text
<normalized-first-author-surname><year>-<short-title-token>
~~~

If that key collides, append a deterministic suffix derived from DOI, PMID, arXiv ID, or another stable identifier. Do not use bibliography order as a suffix. Once assigned, never rename a citekey during the project.

Example BibTeX structure, with placeholders only:

~~~bibtex
@article{<stable-citekey>,
  author  = {<verified author list>},
  title   = {<verified title>},
  journal = {<verified journal>},
  year    = {<verified year>},
  doi     = {<verified DOI if one exists>},
  pmid    = {<verified PMID if one exists>},
  url     = {<authoritative URL>}
}
~~~

Final formatting is generated, never hand-renumbered:

~~~bash
pandoc review_project/<project-id>/manuscript.md --citeproc --bibliography review_project/<project-id>/references.bib --output review_project/<project-id>/rendered/manuscript.docx
~~~

When `citations.target_csl` points to a current, verified file supplied by the user or journal, append `--csl <that-file>`. Do not assume `target-journal.csl` exists.

## claim_ledger.csv schema

Use this exact header:

~~~csv
claim_id,section,claim_text,claim_type,citekey,source_id,source_locator,evidence_excerpt,population_or_dataset,data_split,split_unit,comparator,metric,estimate,unit,uncertainty_interval,direction,access_level,source_role,access_uri,accessed_at,verification_status,verified_by,verified_at,notes
~~~

Field contract:

| Field | Requirement |
|---|---|
| claim_id | Stable project-local ID; reuse it when one claim has multiple source rows |
| section | Stable manuscript section anchor |
| claim_text | Atomic claim, not an entire paragraph; use one metric, one direction, one material claim type, and its own citekey set per row |
| claim_type | factual, quantitative, comparative, directional, priority, regulatory, reimbursement, availability, or synthesis |
| citekey | Existing key in references.bib |
| source_id | DOI, PMID, arXiv ID, registry ID, regulator record ID, or other stable ID |
| source_locator | Page plus section/table/figure/supplement/registry field sufficient to re-find support |
| evidence_excerpt | Short paraphrase or minimal excerpt needed for verification |
| population_or_dataset | Named population, cohort, or dataset, or not_applicable |
| data_split | development, tuning, internal_test, external_test, temporal_test, prospective_test, mixed, unclear, or not_applicable |
| split_unit | patient, study, examination, image, slice, lesion, patch, site, unclear, or not_applicable |
| comparator | Explicit comparator/reference method or not_applicable |
| metric | Exact metric/effect measure or not_applicable |
| estimate | Exact reported value without unit, or not_applicable |
| unit | Percent, probability, mm, seconds, HR, OR, RR, points, or source-defined unit |
| uncertainty_interval | Confidence/credible interval, other uncertainty, not_reported, or not_applicable |
| direction | higher, lower, no_clear_difference, mixed, not_reported, or not_applicable |
| access_level | full_text, abstract_only, metadata_only, official_record, registry, or inaccessible |
| source_role | primary_study, secondary_review, preprint, protocol, conduct_guideline, reporting_guideline, primary_study_reporting_guideline, risk_of_bias_tool, certainty_guidance, registry, regulator, payer_or_coding_authority, dataset_owner, vendor_documentation, software_or_code, correction_or_retraction_notice, or other |
| access_uri | Authoritative URI or an approved opaque local-source identifier; never expose a private local path in a manuscript |
| accessed_at | ISO-8601 access date/time for the exact source version used |
| verification_status | pending, verified, partially_verified, contradicted, inaccessible, or superseded |
| verified_by | Non-empty human ID for verified claims |
| verified_at | ISO-8601 date/time or empty while pending |
| notes | Caveats, adjustment set, threshold, subgroup, version, or conflict notes |

Rules:

- use one row per claim-source pair;
- quantitative and directional prose requires verification_status=verified;
- critical systematic data requires two distinct human extraction decisions in extraction/critical_data.csv; claim_ledger.csv records the human who verified the manuscript claim;
- abstract_only cannot verify architecture internals, priority, subgroup, adjusted-effect, or precise performance claims;
- official regulatory and reimbursement claims require official_record access and a current checked date;
- a missing DOI does not make a study ineligible when another stable identifier exists.

### Migrating a pre-vNext 22-column ledger

A 22-column or otherwise pre-vNext claim ledger is not schema 2.0 and must not be opened and silently reinterpreted under the current header.

1. Preserve the original file unchanged under a dated legacy-import name and record its checksum or other immutable identifier.
2. Create a new claim_ledger.csv with the exact schema-2.0 header above; do not add blank columns to the legacy file in place.
3. Create a dated migration manifest that records the source file, source schema or `unknown`, destination schema `2.0`, every source-to-destination mapping by column name, unmapped fields, row counts, migration author, and migration time.
4. Copy only fields whose meaning is demonstrably equivalent. Explicitly populate evidence_excerpt, split_unit, and source_role when the source supports them; otherwise use a permitted unresolved value or leave the claim pending rather than inferring one from position or context.
5. Set migrated claim rows to verification_status=pending until a named human rechecks the source locator and mapped evidence, then record verified_by and verified_at normally.
6. Record the migration in protocol_deviations.md and update schemas.claim_ledger in review_config.yaml to `2.0` only after validation. Never delete or overwrite the legacy ledger.

Migration is a provenance-preserving transformation, not permission to upgrade claim certainty or fill missing evidence from model memory.

~~~csv
record_id,citekey,exclusion_reason,reviewer_id,adjudication_status
~~~

Full-text exclusions must use protocol-defined reasons. Preserve each independent decision in screening/screening_decisions.csv before adjudication.
For every `record_id` that reaches a screening stage, preserve one original row per human reviewer. A completed systematic gate requires at least two distinct human `reviewer_id` values for each `(record_id, stage)` pair at both `title_abstract` and `full_text`; do not replace original rows with one consensus row.
Every title/abstract record resolved to `include` must appear at full-text screening. `maybe`, `unclear`, and other provisional decisions are not terminal and cannot close the title/abstract stage. No record may disappear between stages: exclusions need a terminal, adjudicated decision and the corresponding exclusion record.

### Formal-route adjudication header

~~~csv
conflict_id,artifact,record_id,decision_group_id,reviewer_1_decision,reviewer_2_decision,resolution,adjudicator_id,resolved_at,rationale
~~~

For extraction and risk-of-bias conflicts, `decision_group_id` must match the immutable group in the originating artifact. For screening conflicts, use `record_id` plus stage in the rationale or artifact reference. Use these machine-auditable terminal values in `resolution`:

- screening: exactly `include` or `exclude`;
- critical-data extraction: `{"adjudicated_value":"<final value>"}` (a plain scalar remains readable for migrated records, but the JSON form is preferred);
- risk of bias: `{"final_judgment":"<one of the preserved reviewer judgments>"}`.

Do not use `N/A`, `not_applicable`, `unclear`, `maybe`, `pending`, or another placeholder as a resolution. The named human adjudicator, timestamp, and rationale are required, and the resolution must agree with the originating artifact rather than replace its independent rows.

## human_review_gate.json

This file is generated only for the systematic route. Its initial contents match the initializer exactly except that the project ID below is a placeholder:

~~~json
{
  "schema_version": "2.0",
  "project_id": "<project-id>",
  "route": "systematic",
  "status": "not_ready",
  "reviewer_ids": [],
  "checks": {
    "title_abstract_screening": "not_ready",
    "full_text_screening": "not_ready",
    "critical_data_extraction": "not_ready",
    "risk_of_bias": "not_ready",
    "certainty_approval": "not_applicable",
    "conflicts_adjudicated": false,
    "ai_assistance_disclosed": false
  },
  "evidence": {
    "title_abstract_screening": "screening/screening_decisions.csv",
    "full_text_screening": "screening/screening_decisions.csv",
    "critical_data_extraction": "extraction/critical_data.csv",
    "risk_of_bias": "risk_of_bias/assessments.csv",
    "certainty_approval": "certainty/assessments.csv",
    "conflicts": "adjudication/conflict_log.csv",
    "ai_disclosure": "AI_USE_DISCLOSURE.md"
  },
  "completed_at": null,
  "completed_by": null,
  "note": "reviewer_ids is the aggregate union across roles; each required stage still needs two distinct humans. LLM agents do not count as human reviewers."
}
~~~

Do not alter the evidence paths. To reach the valid terminal state:

- set status to complete;
- populate reviewer_ids with at least two distinct, non-empty human IDs;
- AI models, bots, agents, automation accounts, and duplicate aliases are invalid reviewer IDs;
- reviewer_ids is the aggregate union of all human IDs used across required stages; each stage may use a different two-person team;
- screening/screening_decisions.csv must contain at least two distinct human IDs for title_abstract and at least two for full_text, preserving the original decisions before adjudication;
- extraction/critical_data.csv and risk_of_bias/assessments.csv must each contain at least two distinct human IDs under their row-level decision contracts;
- set checks.title_abstract_screening, checks.full_text_screening, checks.critical_data_extraction, and checks.risk_of_bias to complete;
- set checks.certainty_approval to complete when a certainty framework or any certainty rows are used; otherwise retain not_applicable and explain that choice in the protocol;
- set checks.conflicts_adjudicated and checks.ai_assistance_disclosed to true;
- resolve review_config.yaml ai_assistance.used to boolean true/false and set human_decision_authority_confirmed to true before completing the gate;
- set completed_at to the completion timestamp and completed_by to the responsible human lead or adjudicator ID;
- do not set status to complete until both original decisions and all adjudications are preserved;
- an incomplete or missing gate blocks systematic Results prose and expert-signoff packaging.
