# review 另一个 agent 的改动

**问题**：另一个 agent（codex）对同一个仓库做了一批大改动——新增两个模块、
两个命令、一层完整性机制，还顺手全量重排了格式。没有 git，没法 diff。
怎么在有限时间里判断它对不对。

## approach

1. **先跑，再读。** `pytest` + `ruff` 是最便宜的第一手信息。
   这次跑出一个反常信号：测试从 89 秒变成 6.4 秒。**异常的"改进"和异常的失败一样值得查**——
   查下来是新增了一个 autouse fixture 把限速等待打掉了，合理。
2. **对可疑的提速，问"它有没有架空什么"。** 全局 stub 掉 `_sleep` 的典型风险是
   让"测试限速本身"的用例空转通过。逐条查了：没有任何测试断言 RateLimiter 真的等待，
   而那条"配额耗尽要快速失败"的测试断言的是最终 `status == "failed"`，不是时间。
   结论是安全的——**但这个结论必须查出来，不能默认。**
3. **用 mtime 代替 diff。** 没有 git 时，`stat -f "%Sm %N" | sort -r` 就是差异视图。
   正是它暴露了真实 run 目录在 17:38–17:40 被写过。
4. **区分"一次性动作"和"代码里的地雷"。** 发现产物丢失后，第一件事不是追问为什么，
   而是 grep `unlink` / `rmtree` / `os.remove`。**如果删除逻辑在代码里，它会再发生；
   如果不在，那只是一次操作。** 这一步决定了它是 P0 还是一条待确认信息。
5. **把每个判断做成可执行的实验。** 怀疑"刚生成的交付物会被标成旧格式"，
   就造两个空文件跑 `verify`，看它到底说什么、退出码是多少。
   （中间还犯了一次错：`cmd | tail; echo $?` 取到的是 `tail` 的退出码，
   得到"strict 无效"的假结论。**管道会吃掉退出码——测退出码就不要接管道。**）

## 判断取舍

- **没有把 codex 的改动往回改。** 它把我写的"估计召回率 X%"改成了
  "两源并集覆盖度"，理由是 Chapman 估的是 PubMed∪OpenAlex 这个二源总体，
  不含 arXiv/CVF/滚雪球，也没验证主题相关性。**它是对的，我原来的措辞在过度声称。**
  review 的目的是让代码变对，不是守住自己写的版本。
- **"登记了却不在"改成 warning 而不是保留 error。** 触发点是用户一句
  "交付物是我删的，为了清理空间"。几 MB 的产物被主动删掉是正当操作，
  报成完整性损坏会让真正的损坏淹没在同级噪声里。
  **同一个信号在不同的使用现实下，正确的严重级别是不同的。**
- **`deliver` 里调了写盘顺序而不是只加登记。** `dois.md` 依赖 `ranked.jsonl`，
  原顺序是先写 dois.md 再写 ranked.jsonl；直接加登记的话记下的是**上一次**的哈希，
  产物刚生成就被判过期。加机制时要顺着数据流检查一遍顺序。
- **日期裁定收窄到 boundary/undated，而不是让 verify 的措辞变聪明。**
  裁定的职责是消解不确定，不是覆盖证据；从职责上堵住，比在下游把错误提示修得更委婉好。

## 可复用的规则

**review 别人的改动时，最先查的不是它改对没有，是它有没有动你不知道它会动的东西。**

正确性问题会在测试里露头；副作用不会。跑一遍测试只能告诉你"新代码自洽"，
它不会告诉你历史产物被重写了、某个目录被清空了、某个全局 stub 顺手关掉了一类断言。
所以顺序是：**先建立"什么被动过"的全景（mtime / 文件清单 / 目录 diff），
再判断"动得对不对"。**

推论：**发现破坏时，先判断它在代码里还是在操作里。**
在代码里是 P0（会重复发生），在操作里是一条要确认的事实——
而这两者的处理方式完全不同，搞混会让你花错力气。
