# 零配置不等于零成本

**问题**：把一条硬编码 DeepSeek 的流水线改成可开源的形态，需要三件事：
LLM 层去厂商化、给没有 API key 的人一条能跑的路、以及别让第一次试用就是 $10 / 3 小时。

## approach

1. **先把"价目"和"端点"从筛选层剥出去。** `providers.py` 只回答三个问题：
   用哪个模型、发到哪个端点、按什么价目算钱。筛选层从此不知道任何厂商的名字。
2. **只内置实测过的价目。** DeepSeek 的两档是跑出来的，其它厂商一律"价目未知"。
   `Usage.cost(pricing)` 在价目为 `None` 时**返回 None 而不是 0**——
   一个说 $0.00 的 dry-run 比一个说"算不出来"的危险得多，人是照着那个数字决定跑不跑的。
3. **不猜端点。** 未知模型且没设 `LITSEARCH_LLM_BASE_URL` 就报错，
   并把内置模型列出来。猜一个端点会让请求发到不存在的地方，报错还毫无线索。
4. **宿主后端走 `claude -p` 子进程。** 不需要任何 key，clone 完就能跑。
   两条路必须产出**结构相同**的判定（同一个 `record_key` 字段名），
   否则同一个 run 里会出现两种格式的判定文件。
5. **先量开销，再定批大小。** 实测 `claude -p` 每次调用有约 20,000 token 的框架开销
   （禁用全部工具后仍有 9,410 创建 + 10,589 读取）。开销**按次**算，
   所以宿主后端的批次从 25 放大到 60。
6. **量完成本才敢写档位表。** 三档的规模/耗时/成本写进 `profiles.py`，
   `lit depths` 直接打给用户看。档位**只做减法**——协议里没启用的源，
   任何档位都不会打开，否则用户会拿到一份自己没声明过的检索策略。

## 判断取舍

- **一开始把宿主后端的成本写成了 "$0（宿主模型）"，实测后改掉。**
  跑 60 条记录，Opus $1.44、Haiku $0.30。订阅用户确实不额外付费，
  但那是**额度内不另计费**，不是不消耗。写 "$0" 会让人按一个假前提去选 systematic。
  改成分列两个后端的成本，宿主那列写"约 $10 等价"。
- **宿主后端默认 haiku，而不是继承会话模型。** 不指定时 `claude -p` 用 Opus，
  贵 5 倍。初筛是照着明确标准做的分类，不需要最强的模型——但这个选择要显式，
  所以给了 `--host-model`。
- **没有把宿主后端做成"上万条也能跑"。** 它在 quick/standard 规模是最优解
  （零配置），在 systematic 规模比 DeepSeek Flash 贵一个数量级。
  文档直接写"上万条请改用 API 后端"，不假装它通用。
- **旧变量名 `DEEPSEEK_API_KEY` 继续认。** 已有用户的 `.env` 不该因为重构而失效。
- **档位不改变严谨度。** 判定规则、去重、时间窗、召回率证据三档完全一致，
  降的只是覆盖面。这句话写进了 `lit depths` 的输出——
  否则"quick"听起来像"糙一点"，而它其实是"少跑几个源"。

## 可复用的规则

**"不需要配置"和"不花钱"是两件事，文档里必须分开写。**
把消耗额度的路径标成免费，用户会照着这个假前提做规模决策——
而他发现真相的时候，已经跑了两小时。

推论：**任何"我们帮你估算成本"的功能，都必须能说"我算不出来"。**
估算器最危险的失败不是估错，是在没有依据时给出一个看起来精确的数。
