# 会翻转的服务让所有对照失效

**问题**：arXiv API 对 litsearch 的全部 11 条检索式返回 HTTP 406，而 curl 手打同一条
却 200。我为此做了五轮排查，前三次结论——「是 httpx 的请求头」「是本机代理」
「是查询语法（`abs:` 前缀 / 日期区间 / max_results）」——**全部被后续实验推翻**。

真实原因：arXiv 的 Fastly 边缘以分钟级在健康和故障之间翻转，故障窗口内对**缓存
未命中**的请求一律 406。证据是响应头里的 `via`：失败时两跳（`varnish, varnish`，
边缘直接挡回），成功时四跳（`google, varnish, varnish, varnish`，到了源站）。

## approach

1. **先问"这个对照有没有区分力"，再看它的结论。** 我那三次错误结论有同一个成因：
   整批 A/B 落在同一个故障窗口里，于是 8 条请求头变体**全部失败**——包括作为
   阳性对照的 `UA=curl/8.7.1`。一个所有分支都同号的对照，信息量是零，
   却长得和"我排除了这个因素"一模一样。
2. **判据写成"必须出现混合结果"。** 对翻转型故障，只有当同一批里既有通过又有
   失败时，比较才成立。定下这条之后，前面那些"确凿的发现"自己就散了。
3. **探活必须和被测对象走同一条路径。** 我写了个「连续 3 次探活 200 就发起续跑」
   的循环，跑了 6 轮、每轮都是探活通过而 11 条全败。因为探活用的是我反复打过
   几十次的 URL——它被 Fastly 缓存了，**源站挂着它照样 200**。探活测的是缓存
   健康，不是源站健康。
4. **量化损失，再决定要不要继续等。** arXiv 整源丢失听起来是灾难，实测语料里
   98 条（23%）已带 arXiv DOI、156 条带 arXiv 标识符——OpenAlex 本身索引 arXiv。
   金标准召回 10/10，窗口外泄漏 0。损失有界，不必阻塞整条流水线。

## 判断取舍

- **修重试而不是修请求。** 客户端侧无解（所有 UA、两种 HTTP 协议、走不走代理
  都一样），能做的只有把 406 当瞬时故障重试。
- **重试集合按源覆盖，不进全局。** 同一个状态码在不同语境下含义相反：406 对
  arXiv 是瞬时故障，对 doi.org 的内容协商却是「这个引文样式不存在」——一个
  永远不会变的答案，重试只会拖慢 `lit deliver`。
- **修了也要承认它不够。** 6 次重试约 60 秒，盖不住分钟级停机。把硬失败变成
  重试后失败是改进，不是解决；报告里那句「arxiv 采集不完整，召回数字是下界」
  仍然要照说。

## 可复用的规则

**服务会翻转时，"我排除了这个因素"和"我没测出区别"长得一模一样。** 判断一个
对照实验是否成立，先看它有没有产生混合结果；全部同号的批次不能用来排除任何
因素，哪怕它包含了你精心设计的阳性对照。

推论：**任何用来给动作开门的探活，都必须和被守护的动作走同一条代码路径、
同一类输入。** 一个被缓存的探活 URL 会让你反复对着一个挂掉的源站发起重试，
而每一轮都显示"检查通过"。
